## Для всіх рівнів

### DEL-01. Доказовий комплект та результат виправлення

Основні матеріали: `docs/source-to-sink.md`, `docs/browser-security-evidence.md` та скріншоти в `docs/lab05-evidence/`. Карта описує два потоки даних: `Incident.Description` і `IncidentComment.Text`, від джерела та збереження в PostgreSQL через API до відображення у DOM.

**До виправлення.** У локальному уразливому стані `3f07849` значення `Incident.Description` відображалося через `innerHTML`. Безпечний навчальний маркер із подією `onerror` установлював на `#lab05-marker-target` атрибут `data-lab05-marker="executed"`. Для Alice та привілейованого глядача Morgan дію було відтворено; Bob не мав доступу до чужого інциденту (`GET 403`). У другому потоці аналогічний ризик містив `paragraph.innerHTML = comment.text`.

**Першопричина.** Недовірені текстові дані з БД потрапляли до HTML-контексту DOM. Валідація введення, збереження в PostgreSQL і JSON-серіалізація самі по собі не роблять `innerHTML` безпечним.

**Виправлення.** Коміт `8b1dc1b`: обидва sink замінено спільною функцією `renderSafeText(element, text)`, яка використовує `element.textContent = text ?? ""`. Значення в API залишилося текстом, проте браузер перестав інтерпретувати його як HTML.

**Повторна перевірка.** Після виправлення маркер для опису й коментаря не виконувався (`null`), HTML-подібні конструкції показувалися буквально. Перевірено лапки, апостроф, Unicode і текст довжиною 3900 символів. Основний клієнт `browser-lab.html` повертав `GET 200`, а авторизація та головна сторінка продовжували працювати під CSP. Підсумковий запуск `dotnet test tests/SecureLab.Api.Tests/SecureLab.Api.Tests.csproj --configuration Release` — **33 успішні, 0 невдалих, 0 пропущених**.

**Залишковий ризик.** Нове використання `innerHTML` з недовіреними даними знову створить XSS-ризик. CSP є додатковим обмеженням, але не замінює безпечний DOM rendering.

**REG-XSS-01.** Передумова: локальна база з тестовими користувачами й інцидентом із канонічним harmless marker. Кроки: увійти як дозволений користувач, відкрити `/browser-lab.html`, прочитати інцидент, перевірити `#lab05-marker-target` та DOM опису і коментарів. Очікування: маркер не виконується, дані залишаються текстом; на `3f07849` той самий маркер виконувався. Докази наведено в DEL-01.

**REG-CORS-01.** У кінцевій конфігурації `ddf9cfa` обидва прямі запити `GET /health` повернули `200 OK`. Для `Origin: http://localhost:4173` відповідь містила `Access-Control-Allow-Origin: http://localhost:4173` і `Access-Control-Allow-Credentials: true`; для `Origin: http://localhost:4174` обидва заголовки були відсутні. Браузерний дослід показав різницю в доступності відповіді JavaScript. Прямий HTTP-клієнт читає відповідь незалежно від браузерного CORS, однак не обходить серверні перевірки доступу.

## Додатково для Добре та Відмінно

**Другий sink і спільний helper.** Для `IncidentComment.Text` використано публічний тестовий коментар із `DbSeeder.cs` (`30000000-0000-0000-0000-000000000005`). До виправлення маркер у коментарі виконувався, після заміни `innerHTML` на `textContent` — ні. Опис і коментарі відображаються через `renderSafeText()`.

**Preflight та cookie-дослід.** Для `4173` preflight `OPTIONS` одержував дозвільні CORS-заголовки; `4174` не отримував `Access-Control-Allow-Origin`. При `credentials: "include"` авторизований запит із `4173` читав відповідь `200`, тоді як JavaScript на `4174` не отримував доступу до відповіді. Без `AllowCredentials()` навіть дозволений origin не міг прочитати credentialed response. Неавторизований запит із `4173` міг прочитати відповідь `401`, що показує незалежність CORS від автентифікації.

**Cookie.** `.AspNetCore.Identity.Application`; домен `localhost`, шлях `/`, `HttpOnly` увімкнено, `SameSite=Lax`, `Secure` вимкнено для локального HTTP, час життя — `Session`. Значення cookie не включено до звіту. Для реального HTTPS-середовища потрібна захищена cookie та окремий аналіз CSRF.

**CORS policy.** `Lab05BrowserProbe` дозволяє тільки `http://localhost:4173`, містить `AllowCredentials()` і реєструється та застосовується лише в `Development`. Порт `4174` не додано до allowlist. Запуск у `Production` окремо не перевірявся; обмеження підтверджено кодом. Навчальні origins не є production-конфігурацією.

**CSP і заголовки.** У кінцевому стані ввімкнено enforcement CSP з `default-src 'self'`, `script-src 'self'`, `connect-src 'self'`, `img-src 'self' data:`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'self'`. Для `style-src` у поточній конфігурації залишено `'self' 'unsafe-inline'`; цей виняток стосується стилів, не скриптів, і має бути мінімізований у production. Спроба завантаження зображення з `4173` блокувалася CSP, вбудовування сторінки в iframe також блокувалося. Перевірено `X-Content-Type-Options: nosniff` (проти MIME-sniffing) і `Referrer-Policy: no-referrer` (щоб не передавати URL джерела); поточному навчальному клієнту передавання referrer не потрібне. `frame-ancestors 'none'` зменшує ризик clickjacking. Після ввімкнення CSP сторінки `/`, `/auth-lab.html`, `/browser-lab.html` працювали; вхід Alice завершився `Login: 204`.

**Короткий review.** XSS — виконання небажаного коду через неправильне трактування даних у DOM; виправляється контекстно безпечним виведенням. CORS — браузерний механізм контролю читання cross-origin response, а не захист API від усіх клієнтів. CSRF — ризик небажаного запиту від імені користувача з автоматично доданими cookies; для змін стану потрібен окремий antiforgery-контроль. Authorization — серверне рішення, чи має автентифікований principal право читати або змінювати конкретний ресурс; CORS його не замінює. Реалізація CSRF-захисту не входила до ЛР 5.

## DEL-03. Відповіді на контрольні питання

1. **Чому значення з БД може залишатися недовіреним?** База зберігає дані, але не гарантує, що введений раніше текст безпечний для HTML-контексту. Тому після читання з БД потрібне безпечне відображення.
2. **Що таке source, transformation і sink?** Source — введене поле `Description`; transformation — передавання через JSON, валідація й збереження; sink — операція вставлення значення в DOM (`innerHTML` або `textContent`).
3. **Чим відрізняються stored, reflected і DOM-based XSS?** Stored використовує збережені дані; reflected одразу повертає введення у відповіді; DOM-based виникає через небезпечні операції клієнтського JavaScript. Ці класифікації можуть перетинатися.
4. **Чому блокування `<script>` не усуває XSS?** Код може виконуватися через інші HTML-елементи, атрибути подій або небезпечні контексти. Потрібно усувати небезпечний sink, а не окремий рядок.
5. **Коли застосовують `textContent`, а коли sanitizer?** `textContent` — коли дані мають бути звичайним текстом; sanitizer — тільки коли вимоги продукту дозволяють обмежену HTML-розмітку. У цій лабораторній HTML не дозволено.
6. **Чому sanitizer не варто писати регулярним виразом?** HTML має складний синтаксис і контексти інтерпретації; регулярний вираз не гарантує коректного очищення всіх комбінацій.
7. **З чого складається origin?** Із схеми, host та порту. `http://localhost:4173` і `http://localhost:4174` — різні origins.
8. **Що містить CORS preflight і хто його ініціює?** Браузер надсилає `OPTIONS` з `Origin`, `Access-Control-Request-Method` та, за потреби, `Access-Control-Request-Headers` перед певними cross-origin запитами.
9. **Хто оголошує CORS і хто застосовує?** Сервер відповідає заголовками CORS, а браузер вирішує, чи дозволити JavaScript прочитати відповідь.
10. **Чому `curl` читає відповідь попри CORS-помилку браузера?** `curl` не застосовує браузерну Same-Origin Policy, але все одно підпорядковується автентифікації й авторизації API.
11. **Чому CORS не замінює authorization та CSRF-захист?** CORS контролює доступ JavaScript до відповіді, не визначає прав користувача і не гарантує блокування небажаних запитів із cookies.
12. **Чому не можна поєднувати wildcard origin і credentials?** Така політика дозволяла б довільним сайтам читати credentialed responses; специфікація CORS і ASP.NET Core не допускають поєднання `*` з `AllowCredentials()`.
13. **Яка межа CSP?** CSP обмежує джерела ресурсів і певні способи виконання скриптів, але не виправляє `innerHTML`. Навіть заблокований CSP маркер може залишати небезпечний HTML-елемент у DOM.
14. **Які ризики зменшують `nosniff`, `Referrer-Policy`, `frame-ancestors`?** Відповідно MIME-sniffing, надмірне розкриття referrer і вбудовування сторінки для clickjacking. Ці заголовки не замінюють перевірки доступу чи XSS-виправлення.


## Межі перевірки

Досліди виконано на локальному навчальному стенді `localhost` з тестовими користувачами; не проводилося тестування production-середовища та сторонніх сайтів. Не реалізовувався окремий CSRF middleware; автоматичний браузерний DOM-тест та режим CSP Report-Only є доповненнями рівня «Відмінно» і не заявляються як виконані. Результат 33/33 стосується автоматичного набору .NET-тестів, а не автоматизації браузерного DOM. Відтворюваність кінцевого стану забезпечує тег `v0.5.0`, а перевірку опублікованої версії виконують через GitHub.

**Висновок.** У ході лабораторної роботи було простежено шлях недовірених даних від API до DOM, відтворено та усунуто XSS у двох текстових полях, досліджено межі CORS і cookie-автентифікації, впроваджено базову CSP та перевірено security headers. Повторні ручні досліди й автоматичні тести підтвердили працездатність виправленого локального застосунку в межах перевіреного сценарію.
