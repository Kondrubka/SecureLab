## 2. Змінений маршрут обробки запитів

До впровадження Identity частина навчальних endpoint використовувала демонстраційний ідентифікатор власника. Після змін маршрут довіри виглядає так:

1. Браузер надсилає `POST /api/auth/login` із введеними даними через same-origin `fetch`.
2. `SignInManager<ApplicationUser>` перевіряє пароль стандартними засобами ASP.NET Core Identity та за успішного входу формує authentication cookie.
3. Під час наступного запиту браузер автоматично надсилає cookie. `UseAuthentication()` перевіряє її та формує `HttpContext.User`, а `UseAuthorization()` застосовує вимоги доступу.
4. `GET /api/me` повертає тільки дозволені поля поточного користувача; `POST /api/incidents` отримує `ClaimTypes.NameIdentifier` із перевіреного principal.
5. Сервіс Entity Framework Core записує інцидент із визначеним сервером `Incident.OwnerUserId` до PostgreSQL. Відповідь API повертається клієнту без внутрішніх облікових даних.

**Ключові файли:** `src/SecureLab.Api/Program.cs`, `src/SecureLab.Api/Scaffolding/Lab03Identity.cs`, `src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs`, `src/SecureLab.Api/Data/Entities/ApplicationUser.cs`, `tests/SecureLab.Api.Tests/AuthenticationSecurityTests.cs`, `tests/SecureLab.Api.Tests/LoginRateLimitTests.cs`, `src/SecureLab.Api/Client/auth-flow.html`, `src/SecureLab.Api/Client/auth-flow.js`.

Ідентифікатор, доданий клієнтом до `X-Demo-UserId` або JSON, не є доказом особи й не використовується як джерело власника. Джерелом довіри є principal, сформований після перевірки cookie сервером.

## 3. Виконані зміни та обґрунтування

### 3.1. Реєстрація, перевірка пароля та DTO

Реалізовано `POST /api/auth/register` із перевіркою обов'язкових полів, довжини імені, email і відображуваного імені та формату введених значень. Пароль обробляє стандартний `UserManager<ApplicationUser>.CreateAsync`; самостійні алгоритми хешування або збереження відкритого пароля не створювалися. Успішна реєстрація повертає `201 Created` і лише `id`, `userName`, `displayName` через окремий `RegistrationResponse`.

Некоректні дані отримують `400 Bad Request`; повторна реєстрація вже наявного імені обробляється як `409 Conflict` із нейтральним повідомленням `Registration failed`. Це усвідомлений компроміс: код `409` зручний для клієнта, але може бути сигналом про зайнятість імені користувача. Відповідь не містить password hash, security stamp, cookie або токена. У таблиці `identity_users` наявне поле `PasswordHash` і відсутнє поле для зберігання відкритого пароля; фактичні значення хешів не виводилися.

### 3.2. Вхід, профіль та вихід

`POST /api/auth/login` використовує `PasswordSignInAsync`, повертає `204 No Content` після успішної автентифікації або `401 Unauthorized` після відмови. Для невідомого імені та неправильного пароля існуючого акаунта перевірено однаковий статус, тип відповіді та стабільні поля Problem Details (без порівняння унікального `traceId`).

`GET /api/me` захищено через `.RequireAuthorization()`. Він отримує `userId`, `userName` та `role` виключно з `HttpContext.User`. Анонімний запит повертає `401` у форматі `application/problem+json`, без HTML-перенаправлення. `POST /api/auth/logout` викликає `SignInManager.SignOutAsync()` і повертає `204`; після цього в тому самому cookie-сеансі `/api/me` дає `401`.

### 3.3. Захищене створення інцидентів

Для `POST /api/incidents` додано `.RequireAuthorization()`. `Incident.OwnerUserId` встановлюється за `ClaimTypes.NameIdentifier` із перевіреного principal. Дані `ownerUserId`, `role`, `status` та `id` не є частиною дозволеного запиту на створення. Це перевірено з користувачем Bob як без поля власника, так і з навмисно підробленим ідентифікатором Alice. Обидва сценарії зберігають власником Bob.

### 3.4. Налаштування cookie

Для стандартної application cookie задано `HttpOnly = true`, `SameSite = Lax` і `SecurePolicy = SameAsRequest` у Development або `Always` в інших середовищах. В інтеграційному HTTPS-сценарії підтверджено фактичну наявність атрибутів `httponly`, `secure` та `samesite=lax` без друку значення cookie.

`HttpOnly` обмежує читання cookie звичайним JavaScript; `Secure` обмежує її передавання HTTPS; `SameSite=Lax` зменшує частину ризиків міжсайтових запитів. Для локального HTTP-з'єднання в Development атрибут `Secure` може відрізнятися від HTTPS-поведінки — це властивість налаштування `SameAsRequest`, а не вимкнення захисту для production.

### 3.5. Обмеження входу й події автентифікації

До `POST /api/auth/login` застосовано політику `login-limit`: **12 запитів за 10 секунд**, фіксоване вікно, `QueueLimit = 0`, автоматичне поновлення квоти. Ключ групи — IP-адреса клієнта; у тестовому host без IP використовується `unknown`. Тринадцятий запит дає `429 Too Many Requests`; після завершення вікна наступна спроба знову проходить до звичайної автентифікаційної перевірки (`401` для неправильних даних).

Вибір IP як ключа не розкриває наявність окремого імені користувача в політиці, але клієнти за спільним NAT можуть витрачати одну квоту. Для реального розгортання потребують окремого аналізу довірені proxy та джерело IP. Структуровані події `Login Success`, `Login Denied` і `Login RateLimited` містять лише назву події, результат і `TraceId`; username, password, password hash, токен, cookie, raw `Authorization` і повний JSON-запит до них не додавалися.

### 3.6. Власний браузерний сценарій

Створено `auth-flow.html` та `auth-flow.js` із п'ятьма етапами: анонімний стан, реєстрація, вхід і профіль, створення інциденту, вихід із повторним `/api/me`. Для запитів використано `fetch` із `credentials: "same-origin"`, а для відображення результатів — `textContent`. Пароль очищується з відповідного input після спроби реєстрації та входу. Статичний пошук у файлі не виявив викликів `localStorage`, `sessionStorage`, `console.*`, `innerHTML` або `document.cookie`.

## 5. Security-сценарій, обмеження та залишкові ризики

**Гіпотеза.** Якщо сервер довіряє `X-Demo-UserId` або переданому клієнтом власнику, можна підмінити контекст користувача без справжньої автентифікації.

**Стан «до».** Анонімний запит до `/api/me` із демонстраційним ID Bob повертав `200 OK` і дані `bob`. Первісна логіка створення інциденту використовувала фіксований ID Alice.

**Першопричина.** Клієнтський header або поле JSON не підтверджують identity; це неперевірені вхідні дані.

**Виправлення.** На захищених endpoint застосовано `.RequireAuthorization()`, ідентифікатор читається лише з `ClaimTypes.NameIdentifier` у `HttpContext.User`, який формується стандартним cookie handler Identity. Для створення інциденту прибрано довіру до клієнтського owner.

**Повторна перевірка.** Той самий анонімний запит до `/api/me` повернув `401 Unauthorized`; анонімний POST також отримав `401`. Після входу Alice `/api/me` повернув її дані, а перевірка A-05 підтвердила, що чужий `ownerUserId` не змінює Bob як власника. Регресійні тести попередніх лабораторних були адаптовані до необхідності cookie-login, без заміни контрактів `201`, `400` і `409` на `401`.

**Залишкові ризики та обмеження.** `SameSite=Lax` не є повноцінним захистом від CSRF; повна анти-CSRF-модель не входила до обраного рівня цієї роботи. Звичайний logout завершує сеанс поточного клієнта, але не доводить негайного відкликання всіх можливих копій cookie. IP-based rate limit може зачіпати кількох користувачів за NAT і потребує врахування proxy в production. Відповідь `409 Conflict` під час повторної реєстрації є зручним контрактом, але може давати непряму інформацію про зайнятість імені. Запитання про 401/403 та більш тонке розмежування доступу до ресурсів залишаються предметом подальших робіт.

Також було перевірено захисні атрибути authentication cookie, однакову зовнішню реакцію на невдалі входи, обмеження частоти запитів із відновленням після завершення вікна та структуроване журналювання без чутливих даних у власних повідомленнях. Власний браузерний сценарій продемонстрував повний цикл від анонімного стану до logout із повторним `401 Unauthorized`.
