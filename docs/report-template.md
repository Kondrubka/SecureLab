## 2. Змінений маршрут

Для реалізованого зведення за критичністю маршрут запиту має такий вигляд:

`Browser → Client/app.js → Presentation/Endpoints/IncidentEndpoints.cs → Application/Incidents/IncidentQueries.cs → SecureLabDbContext → PostgreSQL → API → Client/app.js → Browser`

1. У браузері користувач натискає кнопку завантаження зведення. Функція `loadSeveritySummary()` у `Client/app.js` викликає `apiFetch()`.

2. Клієнт надсилає:

   `GET /api/incidents/severity-summary`

   Якщо вибрано статус, до URL додається параметр:

   `?status=...`

3. Endpoint `GetSeveritySummaryAsync()` у `Presentation/Endpoints/IncidentEndpoints.cs` приймає зовнішній параметр `status`.

   Значення перевіряється через `Enum.TryParse` та явний список дозволених статусів:

   `New`, `Triaged`, `InProgress`, `Resolved`, `Closed`.

   Некоректне значення повертає `400 Validation Problem Details`.

4. `IncidentQueries.GetSeveritySummaryAsync()` у `Application/Incidents/IncidentQueries.cs` формує запит до `SecureLabDbContext.Incidents`.

5. `SecureLabDbContext.Incidents` через EF Core/Npgsql відповідає таблиці `incidents` у PostgreSQL. Запит виконується з `AsNoTracking()`. Якщо передано статус, записи додатково фільтруються.

6. `GroupBy()` та `Count()` агрегують записи за критичністю на стороні PostgreSQL. Дані асинхронно отримуються через `ToListAsync(cancellationToken)`.

7. Отримані групи сортуються в пам'яті у порядку:

   `Low → Medium → High → Critical`.

   Результат перетворюється на `IncidentSeveritySummaryResponse`, що містить поля `severity` і `count`.

8. API повертає `200 OK` із JSON. Клієнт обробляє відповідь і безпечно виводить результат через DOM API та `textContent`.

Для початкових даних запит без фільтра повертає:

`Low: 1, Medium: 1, High: 1`.

Групи з нульовою кількістю інцидентів не додаються.

## 3. Виконані зміни

Реалізовано endpoint:

`GET /api/incidents/severity-summary`

який повертає кількість інцидентів для кожного наявного рівня критичності.

Додано:

* необов'язковий параметр фільтрації `status`;
* перевірку значення `status` через `Enum.TryParse` та список дозволених статусів;
* повернення `400 Validation Problem Details` для недопустимого статусу;
* агрегування інцидентів за `Severity` через `GroupBy()` і `Count()`;
* асинхронне виконання запиту через `ToListAsync(cancellationToken)`;
* сортування груп у порядку `Low → Medium → High → Critical`;
* окрему модель відповіді `IncidentSeveritySummaryResponse`;
* структуроване журналювання кількості груп та застосованого статусу;
* клієнтську функцію `loadSeveritySummary()`;
* стан завантаження та блокування кнопки під час виконання запиту;
* повідомлення для порожнього результату;
* фіксоване повідомлення про помилку без виведення внутрішніх деталей сервера;
* безпечне відображення отриманих даних через `textContent`.

Схема PostgreSQL для реалізації зведення не змінювалася.

Також доповнено документацію архітектури описом наскрізного маршруту запиту, меж довіри та процедури відновлення початкових навчальних даних.

## 5. Security-сценарій

### Гіпотеза

Поля інциденту надходять із PostgreSQL і є недовіреними даними. Якщо значення `description` вставляти в DOM як HTML, спеціально сформований вміст може бути інтерпретований браузером як розмітка або JavaScript.

### Стан «до» перевірки

У навчальній базі PostgreSQL присутній інцидент, поле `description` якого містить текст із тегом `<script>`.

Це дозволяє перевірити поведінку клієнта при отриманні потенційно небезпечного HTML-вмісту.

### Мінімальний локальний PoC

Було відкрито деталі інциденту, в `description` якого збережено `<script>`.

Одночасно через PostgreSQL було перевірено, що відповідний рядок справді зберігається в базі даних, тобто значення не було попередньо видалене або замінене на сервері.

### Спостереження

API повернув значення поля клієнту, але браузер показав `<script>` як звичайний текст.

JavaScript із цього значення не виконався.

### Першопричина потенційного ризику

Дані з PostgreSQL не можна автоматично вважати безпечними. Вставлення таких даних через HTML-інтерпретуючі DOM API створило б ризик XSS.

### Виправлення

Клієнт формує DOM-вузли та записує недовірені значення через `textContent` / `createTextNode`, а не вставляє їх як HTML.

Таким чином символи `<` і `>` залишаються частиною текстового вмісту та не створюють HTML-елементи.

### Повторна перевірка

Після завантаження інциденту з тестовим `<script>`:

* сторінка працює нормально;
* текст відображається буквально;
* JavaScript не виконується;
* помилок, спричинених виконанням тестового значення, не спостерігається.

### Позитивна регресія

Звичайні значення `title`, `description`, `severity` та `status` продовжують коректно відображатися після застосування безпечного способу роботи з DOM.

Endpoint зведення також виводить отримані від API значення через `textContent`.

### Залишковий ризик

Безпечне відображення на поточній сторінці не гарантує безпеку інших майбутніх клієнтів або нових місць виведення даних.

Якщо надалі недовірені значення будуть вставлятися через HTML-інтерпретуючі API, ризик XSS може виникнути повторно. Тому дані із зовнішніх джерел і БД потрібно й надалі виводити через безпечні DOM API.

## 6. Висновок

У лабораторній роботі було досліджено наскрізний маршрут HTTP-запиту у вебзастосунку «Трекер інцидентів» — від дії користувача в браузері через Presentation та Application шари до PostgreSQL і назад.

Реалізовано endpoint `GET /api/incidents/severity-summary`, який виконує агрегування інцидентів за критичністю та підтримує необов'язкову фільтрацію за статусом. Для некоректних значень статусу реалізовано відповідь `400 Validation Problem Details`, а за відсутності відповідних інцидентів API повертає порожній масив.

Перевірено позитивні та негативні сценарії роботи API, відповідь `404` для неіснуючого інциденту, а також безпечне відображення недовірених даних у браузері. Значення `<script>`, збережене у PostgreSQL, відображається як звичайний текст і не виконується браузером.

Автоматизовані перевірки завершилися результатом `8 passed, 0 failed, 0 skipped`.

Після відновлення навчальної бази даних повторна перевірка підтвердила відновлення початкового seed: фільтр `Triaged` повернув інцидент `Medium / Triaged`, а зведення без фільтра — `Low: 1`, `Medium: 1`, `High: 1`.

Таким чином реалізована функціональність працює відповідно до очікуваної поведінки, а взаємодія між клієнтом, API, Application шаром та PostgreSQL підтверджена практичними перевірками.
