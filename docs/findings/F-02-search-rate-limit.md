# F-02 — Відсутність rate limiting для пошуку інцидентів

**Дата:** 17.11.2026
**Статус:** Fixed — retest PASS, 17.11.2026
**Категорія:** Availability / Resource Exhaustion

## Виявлений недолік

GET /api/incidents/search не використовує окремої
політики обмеження частоти HTTP-запитів.

Наявна політика login-limit захищає лише маршрут входу.

## Відтворення до виправлення

Маршрут:
GET /api/incidents/search?q=zz-no-match

Умови:
- Локальний API: http://localhost:5080
- База даних PostgreSQL доступна
- 15 послідовних пошукових запитів

Фактичний результат:
- Загалом: 15 запитів
- HTTP 200: 15
- HTTP 429: 0
- Тривалість: 0,4615312 секунди

## Ризик

Велика кількість пошукових запитів може
створювати надмірне навантаження на API та БД.

Наявний тест підтверджує відсутність обмеження
для короткої серії, а не реальну відмову сервісу.

## План виправлення

Додати окрему політику search-limit.
Розділити лічильники за незалежними ключами.
Перевірити HTTP 429 та відновлення після вікна.
Зберегти працездатність login-limit.

## Виправлення

Додано політику search-limit для GET /api/incidents/search.

Алгоритм: Fixed Window.
Квота: 5 запитів за 10 секунд.
QueueLimit: 0.
AutoReplenishment: true.

Для авторизованих користувачів partition key
формується на основі перевіреного UserId.
Для анонімних користувачів — за IP-адресою.

Authentication виконується перед RateLimiter.
Наявний login-limit збережено.
У журналі розділено події Search та Login.

## Залишковий ризик

In-memory rate limiting діє в межах одного
екземпляра застосунку. Для кількох серверів
потрібне узгоджене або централізоване обмеження.

Локальний тест не є навантажувальним
випробуванням на відмову в обслуговуванні.
